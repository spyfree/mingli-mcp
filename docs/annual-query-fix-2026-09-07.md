# 咨询流年时间口径修复

## 已复现的问题

本机 MCP 的 `get_bazi_fortune` / `get_ziwei_fortune` 对 2027、2030、2033、2036
年 1 月 1 日分别返回丙午、己酉、壬子、乙卯。改查 3 月 1 日后，两者分别返回
丁未、庚戌、癸丑、丙辰。2033 年年初返回的紫微四化也与历史正文一致。
这证明年初取数后扩写全年是可复现机制；管理员导出未含工具调用参数，不能据此
断言历史请求实际用了 1 月 1 日。

## 改动与接口

- MCP 两个运势工具增加互斥的 `query_year` / `query_date`。前者为公历全年，
  返回 `query_scope: calendar_year`、`query_year`、连续覆盖全年的两个 `periods`。
  各段含流年及该段起始日的大运/大限背景，不含日、月运势，避免伪造日级证据。
- 日期结果增加 `time_basis`：公历查询年、实际干支年、换年规则及干支适用区间。
  区间使用 `[valid_from, valid_until_exclusive)`。八字保留既有立春**日**换年算法，
  未更改为时刻级算法；紫微使用农历正月初一。
- 紫微 JSON 基本信息的 `四柱` 改称 `农历干支`，并在同一 JSON 对象中说明
  农历年月与八字立春/节令年月的差异。其他外部消费者需要迁移该字段名。
- Worker 保留省略日期时查询今天的行为；显式空值、非法日期、裸年份、同时提供
  年份和日期均返回可修正的工具错误，不再静默查询今天。
- 系统指令明确全年分段查询、具体日期查询、本命盘复用和新增年份补取的边界。
- 证据提取只接受查询年匹配、两段连续覆盖全年的响应。全年证据不会算作日级证据。
  年度证据在会话内部持久化（最近 60 条），供同年份追问复用；更换草稿资料时清除。
  不向客户端或管理员正文导出暴露内部证据。
- 对非具体日期问题的显式年度流年断言增加缺证据重试和六语言局限说明。
  合盘需要双方证据。此规则是保守的文本启发式，不能替代逐条命理事实校验；
  重试后仍缺证据时沿用现有降级交付策略，不声称能拦截所有错误。

## 发布顺序

先发布 MCP Python 服务与同步生成的 `cloudflare/mcp-catalog.json`，验证两个工具的
`query_year` 实际可调用，再发布咨询 Worker；站点发布包含新增局限说明的翻译。
不要只更新静态 catalog 而保留不支持年度参数的 Python 后端。

本次不包含线上部署。历史会话不会自动获得新年度证据，首次再次作全年判断时需补取。
没有修改免费额度策略，也没有改写 Claude 的历史审查记录。

## 回归验证范围

- 原四组年份、年初/年中查询、2027 年两套换年边界。
- JSON 农历干支口径、无效/冲突查询参数、年度响应完整性。
- 同年份证据复用、新年份追问、合盘一方缺证据、具体日期与普通建议不误拦。
- 证据持久化且不进入客户端响应；既有额度与会话测试。
